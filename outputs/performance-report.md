# Скорость ответа VoltYo‘l

## Замеры до и после

Замеры на одном компьютере, сохранённые реальные станции в центре Ташкента, 5 прогонов каждого варианта. Подготовка ответа проверялась с настоящими PostgreSQL, Redis и отрисовкой карты; отправка трёх сообщений заменялась имитацией. Для проверки соединения с Telegram выполнялся настоящий read-only `getMe`.

| Этап | До | После |
| --- | --- | --- |
| Медиана подготовки повторного ответа, без доставки | 1,2714 с | 0,0094 с |
| Первый рендер карты после изменения кода | — | 1,7412 с |
| Медиана чтения готовой карты из кэша, 4 последующих прогона | — | около 0,0024 с |
| Запрос Telegram `getMe` с новым соединением, медиана 3 запросов | 1,184 с | — |
| Запрос Telegram `getMe` по уже открытому соединению, медиана 2 запросов | — | 0,206 с |
| Картинка при первой загрузке в Telegram | PNG, 427 513 байт | JPEG, 121 490 байт |

Серверная подготовка повторного ответа ускорилась примерно в 135 раз. Изображение для первой загрузки уменьшено на 71,6%. Первое открытие соединения Telegram после обновления заняло 1,923 с; его стоимость остаётся, но больше не повторяется для каждого сообщения.

Эти результаты **не означают доставку всего ответа за 0,0094 с**. Это только серверная подготовка при попадании в кэш. `getMe` измеряет запрос к API, а не доставку картинки или показ сообщения в клиенте Telegram.

## Изменения

- Общий пул соединений для отправки карты и рекомендаций.
- Кэш полностью готовой карты; повторная отрисовка не нужна.
- Повторная отправка через сохранённый Telegram `file_id`, когда он доступен, без загрузки картинки. Отказавший `file_id` с HTTP 400 заменяется новой загрузкой.
- JPEG для отправки; PNG сохраняется для предпросмотра.
- Общий лимит ожидания Overpass 4 с вместо последовательных HTTP-таймаутов до 20 с на каждый сервер. Это лимит этапа Overpass, а не всего поиска: резервный POI-поиск и сеть имеют собственное время выполнения.
- После ошибки Overpass пропускается на 60 с. Контроль с имитацией зависшего источника: первый отказ через 4,0045 с, повторный — сразу.
- Для входящего Telegram polling connect timeout сокращён с 40 до 5 с. Ожидание новых событий long polling сохраняется.
- Добавлен журнал `work/latency.jsonl` с реальными временами поиска, карты, API и общего ответа, без текста сообщений, координат, chat ID или токена.

## Проверка и границы

Все 31 тест прошли. В том числе проверены кэши, повторное использование соединения и Telegram `file_id`, перезагрузка отвергнутого фото, JPEG и тайм-аут/пауза неисправного источника. Приложение перезапущено, `/health` вернул HTTP 200 в режиме polling.

Полный контрольный ответ на настоящую геопозицию пользователя ещё не измерен в этом отчёте. Для этого включён журнал: после отправки геопозиции можно определить время до принятия Telegram первого и последнего сообщения. Время отображения на телефоне этим способом не измеряется.
